## 01 / 背景与痛点（Why）

求职沟通中最大的痛点是机械性的重复与高注意力的消耗：

1. **破冰成本高**：每个岗位都要仔细看职位描述（JD），提炼对应技能点并撰写个性化打招呼语；如果用千篇一律的模板，HR 回复率极低；如果逐个手工定制，几十家投下来耗时数小时。
2. **多线沟通易遗忘**：同时推进多家公司的面试与答复时，沟通进度全靠脑子记或手工填 Excel，稍有疏漏就会弄混岗位要求。
3. **敏感数据与隐私担忧**：求职者的简历、聊天记录与投递意向属于强隐私数据，市面上许多 SaaS 工具需要将数据上传到其私有服务器，存在泄露隐患。

我需要一个**内嵌在浏览器内、离线优先、注重隐私的生产力副驾**。

## 02 / 解决与实现（Built）

我开发了这款基于最新 Chrome Extension Manifest V3 规范的求职辅助扩展：

- **DOM 智能感知与招呼语生成**：浏览岗位页面时，Content Script 自动提取职位关键技能要求与痛点，结合用户自身优势，一键生成带技能匹配与反问钩子的个性化开场白。
- **侧边栏消息辅助（SidePanel）**：在聊天页面呼出侧边抽屉，快速粘贴或一键读取 HR 最新提问，AI 提供专业/自然等多版本候选回复供用户确认。
- **本地岗位资产库**：采用浏览器内置 IndexedDB 自动归档浏览与投递过的职位，支持状态标记、搜索与 JSON 本地导出。
- **本地数据存储**：API Key 与岗位数据保存在本地 `chrome.storage.local` 和 IndexedDB，无需云端中转服务器。

| 模块 | 技术选型 | 关键职责 |
|---|---|---|
| **页面感知** | Content Script | DOM 解析与监听、JD 核心字段抽取、操作按钮注入 |
| **后台路由** | Service Worker (MV3) | 后台消息转发、大模型 API 调用、跨标签页状态协调 |

| **本地存储** | IndexedDB / chrome.storage | 岗位卡片索引、投递状态管理、本地存储密钥 |

## 04 / 验证与实际表现（Result）

- **招呼语辅助**：浏览职位时自动抓取 JD 关键信息生成候选开场白，由逐字手写变为选定微调，减轻重复输入成本。
- **生成沟通钩子**：结合职位痛点与个人技能点生成针对性问题与开场白，用于破冰沟通与 HR 消息应答。
- **本地数据留存**：投递记录与浏览岗位保存在浏览器本地，支持 JSON 导出归档，不依赖第三方云端。

## 05 / 经验与踩坑（Notes & Takeaways）

1. **Manifest V3 的非持久化生命周期**：
   MV3 的 Service Worker 在空闲约 30 秒后会被浏览器主动挂起。绝不能在后台全局变量中暂存会话状态，所有上下文和配置必须实时写入 IndexedDB 或 `chrome.storage`。
2. **SPA 页面异步 DOM 的监听与处理**：
   现代招聘平台普遍为单页应用（SPA），用户切职位时 URL 可能不刷新或异步延迟渲染。必须利用 `MutationObserver` 结合去抖动（Debounce）逻辑监听容器变动，防止抓取空数据或重复触发。
3. **架构安全与隐私**：
   插件不自建数据收集后端：无私有中转服务器，模型请求由浏览器直连用户配置的模型端点。
