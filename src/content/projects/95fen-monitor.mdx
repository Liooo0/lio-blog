## 为什么做这个

我关注球鞋上新，但 95分 App 没有"关注品牌上新提醒"，只能自己一遍遍刷列表。新品窗口很短，看中的款式晚看到几小时可能就没了。那就自己造一个监控：新鞋上架 → 自动判断是不是我要的 → 微信推给我。

## 整条链路

```
定时轮询 App API → 规则筛选 → 24h 窗口过滤 → SQLite 去重
      → LLM 看图识鞋精筛 → wxpusher 微信推送（多条合并一条）
```

- **规则筛选** — 品牌 / 款式白名单、排除词、价格区间，全部写在 `config/config.yaml`
- **时间窗口** — 只监控最近 24 小时内新上架的商品，首次运行进"基线模式"只记录不推送，避免一上来刷几十条
- **SQLite 去重** — 推过的商品本地留档，不会重复打扰
- **LLM 精筛** — 规则过了再让 qwen3.8-max-preview 看商品图"识鞋"，判断是不是我真正想要的款式，推送时附 AI 理由
- **微信推送** — 通过 wxpusher 把多条命中合并成一条 markdown 消息：标题、价格、品牌、商品图、链接、AI 理由，一屏看完

## 最难的部分：API 签名逆向

95分 App 的接口（`/api_goods/list/v3.0`，逆向自 App 3.31.52）带签名校验。这一夜的核心攻坚就是把签名算法还原出来——**HmacSHA256**，请求头里还要带设备指纹相关的 SK/SKC。签名跑通那一刻，整个监控才算真正立起来。

## 风控边界：token 为什么要人工刷新

access_token 有效期约 30 天。95分的登录受数美设备指纹风控保护，**无法纯程序化获取**——游客 token 会被 97999/90406 拦下来。所以我没有硬绕，而是把边界划清楚：

- 程序自动检测 token 失效（识别 97999/90406 错误码）
- 失效后跑一键刷新脚本：模拟器登录一次（约 1 分钟），脚本自动从 MMKV 提取凭据、真实请求验证、写回配置

风控的事交给规则，人只出这 1 分钟。这是整个系统里唯一需要人工参与的环节。

## 实际效果

- **79 项测试全绿**（pytest），含筛选全链路 + E2E mock
- 微信推送真实发出（wxpusher 返回 code=1000）
- 挂上 cron 后每 8 分钟轮询一次，安安静静，只在有我想要的鞋时才响

## 最新进展（2026-08-05）

- **监控正式上线**：cron 每 8 分钟自动巡检，已稳定运行
- **推送安全加固**：发现并修复"未配置 uid 会群发全部订阅者"的隐患——现在 uid 必须显式配置，只推给指定的人，谁也别想被误打扰
- **修复一个竞态 bug**：换 token 后首轮基线 + LLM 精筛会超过 8 分钟，cron 并发会导致重复推送——加了单实例锁，基线轮跳过 LLM，省时又省钱
- 测试从 79 项涨到 **95 项全绿**
