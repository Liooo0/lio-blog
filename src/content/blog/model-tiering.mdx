手上有 7 个项目在调大模型 API：装修获客 bot、求职自动化、Chrome 扩展、数据仪表盘、桌面应用、模型竞技场……今天把里面的模型名盘了一遍，乱成一锅粥：

- **renovation-bot**：3 个文件全是上一代的 `deepseek-chat`
- **liodesktop**：写死旧模型名，连 UI 占位符都是旧的
- **job-hunter**：唯一用了新 Flash 的，孤零零一个
- **llm-arena**：反倒最规范，Flash + Pro 双接，还挂着 6 个对比基准

没人管的话，这套东西会烂掉。今天把它定下来。

## 规则就三条

**1. Flash（`deepseek-v4-flash`）是生产默认。** 客服对话、批量回复、自动投递这些高频调用，全走它。理由很朴素：便宜、快、稳。这些项目一天几百次调用，成本差着一个数量级，省下来的钱不值得拿去烧 Pro。

敢这么定的底气是跑过数——63 题 × 7 模型的对战记录在[上一篇](/blog/llm-arena-benchmark/)，同一道题质量打平、成本差 6 倍，这里不重复贴表了。

**2. Pro 只留给复杂推理。** liodesktop 的模型传闻深度核验（多路证据交叉判断真伪）、llm-arena 的 benchmark。这些任务慢一点无所谓，推理质量必须拉满。

**3. llm-arena 必须双接。** 它是我的选型依据仓库。只接一家平台的竞技场，说不了公道话。

## 落地全是体力活

规则一分钟定完，改起来是 7 个项目的零敲碎打。renovation-bot 三个文件、boss-helper 两个 JS、liodesktop 的 adapter 加 UI 占位符……全是同一个替换，但每个项目结构都不一样。这种活没有技术含量，只有出错概率。

改完不算完。每个项目发一条真实请求确认，不跑一遍心里没底。llm-arena 还顺手实测了一把并发对战：那次 Flash 跑了 94 秒、Pro 只要 5 秒，一看就是代理抖动，不过至少证明两条通道都是活的。

## 然后栽在 git 上

全部 commit 完，推 GitHub，4 个仓库一起被拒——"remote contains work that you do not have locally"。

原因：我埋头改的这几个小时里，远端 main 合进了 4 个优化 PR（SSE 流式、双盲对决、规则引擎）。本地和远端在 main 上分叉了。

只能 rebase，把改动重新叠到最新 main 上。其中 2 个仓库起了冲突：

- **liodesktop**：PR 重构了 deepseek.py 的 import，跟我加的分层常量撞在文件头。手工合并，两边都要
- **renovation-bot**：PR 的对话轮次截断逻辑，跟我改的模型名挤在同一个 dict 里。截断保留，名字换新

教训值 4 次 rebase：**动手改之前，先 `git fetch` 看一眼远端。** 还好全是自己的仓库，没坑到别人。

## 现在长这样

```
deepseek-v4-flash ── 生产默认：renovation-bot / job-hunter /
                    boss-zhipin-helper / jobintel-dashboard / liodesktop 日常
deepseek-v4-pro   ── 复杂推理：liodesktop 深度核验 / llm-arena benchmark
llm-arena         ── 双接 + 6 个对比基准模型，用对战数据支撑选型
```

全部推完，4 个仓库和远端完全同步。分层规则写进了各项目的 CLAUDE.md，以后新项目进来，第一件事就是认领自己的档位。
